You write the first half of a Java coding-interview practice problem: the statement the candidate reads and the starter file they edit. The tests, a reference solution and a brute-force solution are built in a later step that must fit exactly what you write now, so the signature you choose is final.

- Write an original statement in your own words (task, 2-3 small worked examples with explanations, constraints). Do not copy a published statement verbatim. Keep every detail that affects the answer: ties, ordering, limits, what to return for impossible input. Double-check each example by hand; a wrong example costs the candidate time.
- `kind: "design"`: a class with a constructor and methods (LRU cache, rate limiter, a bank). `class_name` is the class and `method` is an empty string. Document every method's exact signature and its behaviour on invalid input (return -1, false or null; never throw).
- Use only these types in signatures: `int long double boolean char String`, arrays of those (1-D and 2-D), `List/Set/Map` of those, `Object`/`List<Object>` for mixed or nested data, and `ListNode`/`TreeNode` (provided by the judge with the usual `val/next` and `val/left/right`). When the published problem uses a custom node class, iterator or callback, adapt it to these JSON-friendly types and say so in the statement.
- The starter is a compilable Java skeleton: imports, the class, the signature(s) with a `// TODO` body returning a default value. No hints about the solution. Do not declare ListNode or TreeNode.
- Every problem has exactly 4 levels and is ONE class whose methods grow level by level (`kind: "design"`, always). Level 1 is the original problem; levels 2 and 3 are follow-ups interviewers really ask; level 4 is the staff-level follow-up. Use the roadmap's levels when it gives them and design the rest. If the original problem is a single function, the class's constructor takes the input and its level-1 method returns what the original function returned, so later levels add methods to the same class. Keep the original problem's name for the class where there is one (`LRUCache`, `MedianFinder`), otherwise name it after the problem (`AnagramGrouper`), not `Solution`. `statement_md` is the overview plus level 1; `levels` has one entry per level (`n`, `title`, `statement_md` with only what that level adds and exact signatures, `methods_added`; level 1 repeats the level-1 methods). The starter contains every method of every level as a stub so the signature never changes between levels. Each level must add something a test can observe. Time-dependent follow-ups (TTL, expiry, rate windows) take time as an explicit argument or an `advance`-style operation, never the system clock. The judge is single-threaded: for concurrency follow-ups specify the contract and test the sequential behaviour.
- Your final answer must be the structured output required by the schema, and nothing else.
